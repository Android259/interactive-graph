# Локальный запуск: как раздаются ядра и память

Заметка про `scripts/run_local.sh` на этой машине: что за железо, как между работами
делится счёт, что было изменено 2026-08-06 и что трогать нельзя.

## 1. Железо

Замерено на этой машине (`lscpu`, `/proc/meminfo`, `/sys/devices/system/cpu/`):

| | |
|---|---|
| Процессор | AMD Ryzen 5 5500U |
| Настоящих ядер | **6** |
| Показывает `nproc` | **12** — каждое ядро числится за двоих; второе «место» даёт не +100% скорости, а примерно +25% |
| Кэш-домены (L3) | **два по 4 МиБ**: ядра `0-5` и ядра `6-11` |
| Память | 13.8 ГиБ |
| Swap | 4 ГиБ, из них 726 МиБ уже занято |

Два кэш-домена — важная деталь. Кэш это быстрая память рядом с ядрами, куда
складывается то, с чем работа сейчас возится. У ядер `0-5` он свой, у `6-11` свой.
Если работу перекинуть из одной группы в другую, накопленное в кэше пропадает и
данные приходится тащить из обычной памяти заново. Модель в этом проекте весит
около 3 МБ, то есть почти весь домен целиком.

## 2. Как счёт распределяется сейчас

Арифметика в `run_local.sh`, строки 359-436:

```
nproc                  = 12          # не 6: считаются «места», а не ядра
RESERVED_CORES         = 12 / 4 = 3  # придержано, чтобы ноутбук не подвисал
usable_cores           = 12 - 3 = 9

лимит по памяти        = (свободно - 2 ГиБ) / 2 ГиБ на работу = 4

LOCAL_JOBS             = min(9, 4) = 4    # памяти хватает на 4 работы
OMP_THREADS_PER_JOB    = 9 / 4     = 2    # 9 «ядер» делятся на 4 работы
```

Итог: **4 процесса, в каждом по 2 потока, всего 8 потоков на 6 настоящих ядер.**

Что из этого измерено на живом гриде (4 работы, конфиг
`bbp_fa_edge_curent_..._batch8`, 802825 параметра):

| | |
|---|---|
| CPU на процесс | ровно **200%** (= 2 ядра) |
| Загрузка машины | 75-85%, простой 13-24% |
| RSS на процесс | 1.3 ГиБ (из них приватная куча 738 МиБ) |
| Живых данных в этой куче | 89 МиБ (строка `cache warmed` в логе) |
| Темп | ~2.3 минуты на эпоху, 150 эпох ≈ 6 часов на работу |

Два вывода из этих чисел:

1. **Упирается в процессор, а не в память.** 8 потоков на 6 ядер — работы стоят в
   очереди друг за другом.
2. **Работ всего 4 из-за памяти.** Ядер 6, работ 4, поэтому лишние ядра розданы
   уже запущенным работам по второму — иначе 2 ядра простаивали бы.

## 3. Что изменено 2026-08-06

Три правки. Ни одна не меняет число потоков, поэтому все числа в метриках
остаются прежними до последнего знака.

### 3.1 Привязка работы к одному кэш-домену — `run_local.sh`

Перед `python3` подставляется `taskset -c`, домены читаются с самой машины
(`/sys/.../cache/index3/shared_cpu_list`), работы получают их по кругу:
работа 0 → `0-5`, работа 1 → `6-11`, работа 2 → `0-5`, и так далее.

Зачем: система больше не перекидывает потоки между группами ядер, накопленный
кэш не теряется. Машина без `taskset` или без этой информации в `/sys` работает
как раньше, без привязки.

В шапке лога появляется строка:

```
  pinning: 2 cache domain(s), one per job round-robin: 0-5 6-11
```

### 3.2 `OMP_WAIT_POLICY=PASSIVE` — `run_local.sh`

Работа считает в 2 потока: матрица делится пополам, и тот поток, что закончил
раньше, ждёт второго. По умолчанию он ждёт, крутя пустой цикл — полезной работы
ноль, но ядро для системы занято, и соседнюю работу на него не пустят. При
`batch=8` таких ожиданий тысячи в секунду.

`PASSIVE` — ждущий поток засыпает и освобождает ядро. Настройка касается только
того, что поток делает **в ожидании**; сколько потоков и как делится матрица — не
меняется.

### 3.3 Возврат освобождённой памяти — `run_local.sh` + `training/new_train.py`

Что происходило:

1. `Dataloader.py:132` — читается `lipid_SMILES_embedding_deterministic.pkl`,
   280 МБ, целиком в память.
2. `new_train.py`, `warm_caches()` — из него отбираются нужные 410 липидов, это
   89 МиБ.
3. `Dataloader.py:425`, `release_source_artifacts()` — исходная таблица больше
   не нужна, `self.smiles_encoding = None`, Python её удаляет.
4. **Чего не происходило:** `malloc` освободившееся ядру ОС не возвращал, держал у
   себя. Для системы процесс продолжал занимать эту память.

Отсюда и расхождение 738 МиБ кучи против 89 МиБ живых данных.

Изменения:

- `MALLOC_ARENA_MAX=2` в `run_local.sh` — `malloc` не разбрасывает память по
  восьми отдельным кучам, из которых её потом не собрать.
- `_return_freed_heap_to_kernel()` в `new_train.py`, вызывается сразу после
  `release_source_artifacts()` — `gc.collect()` плюс `malloc_trim(0)`, то есть
  прямая команда «свободное отдай ядру сейчас». На этой машине проверено, вызов
  возвращает `1`. На системах без `malloc_trim` (musl, macOS) шаг пропускается.

Ожидаемо: минус 300-500 МБ на работу. Это не ускорение само по себе — это запас,
чтобы часть обучения не уехала в swap (на диск, а он в тысячи раз медленнее
памяти).

## 4. Что трогать нельзя

Всё перечисленное **меняет числа в метриках**, а значит новые прогоны становится
не с чем сравнивать.

- **`OMP_THREADS_PER_JOB` / `MAX_OMP_THREADS_PER_JOB`.** Потоки делят матрицу на
  куски и складывают частичные суммы. Другое число потоков — другой порядок
  сложения — другие последние знаки.
- **`num_workers`.** Уже измерено и записано в `dataloader/AGENTS.md:151`:
  переключение сдвигает порядок перемешивания данных, валидационная сбалансированная
  точность поехала с 0.489583 на 0.500000.
- **`batch`.**
- **`MKL_ENABLE_INSTRUCTIONS`** и прочая подмена вычислительных ядер MKL.

**А что менять можно свободно — это число одновременных работ** (`LOCAL_JOBS`).
Работы считают независимо друг от друга, соседи на результат не влияют никак.

Оговорка про воспроизводимость: `MKL_DYNAMIC` по умолчанию `TRUE`, то есть MKL
вправе сам урезать число потоков под нагрузкой. Строгого совпадения до последнего
знака между уже посчитанными прогонами это не гарантирует. `MKL_DYNAMIC=FALSE`
это чинит, но сдвинет числа относительно всего, что уже посчитано, поэтому не
сделано.

## 5. Не сделано, но возможно

1. **Шесть работ вместо четырёх.** После правки 3.3 памяти должно хватить на 6, и
   тогда каждой работе достанется своё ядро без дележа. Общая пропускная
   способность вырастет примерно на 15%, но каждая отдельная работа станет
   медленнее примерно на четверть. Запускается так — `OMP_THREADS_PER_JOB=2`
   **обязательно указывать явно**, иначе скрипт посчитает `9/6 = 1` и результаты
   поедут:

   ```bash
   LOCAL_JOBS=6 OMP_THREADS_PER_JOB=2 bash scripts/run_local.sh <args_file>
   ```

2. **Таблицу эмбеддингов не читать в каждый процесс.** Сейчас файл на 280 МБ
   читают все 4 работы, каждая себе. Если перевести его в формат, который
   подключается к файлу напрямую (`torch.load(..., mmap=True)`), копия будет одна
   на всех. Байты тензоров те же, результаты те же.

3. **Поставить torch без CUDA.** Стоит сборка `2.12.0+cu130`, а видеокарты для
   счёта тут нет. Из-за неё в каждый процесс подгружаются `triton` (61 МиБ),
   `libcublasLt` (50 МиБ), `nvrtc` и `nvJitLink` (28 МиБ). Требует проверки одним
   прогоном на совпадение метрик.

4. **Померить эффект правок.** Оценка «10-20%» — это оценка, а не измерение.
   Мерить коротким прогоном (3 эпохи) через `scripts/profile_training.py`, когда
   машина освободится: замер сам занимает ядра и на загруженной машине соврёт.
