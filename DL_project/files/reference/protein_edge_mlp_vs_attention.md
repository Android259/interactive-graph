# `--protein_edge_mlp` vs `--protein_edge_attention`: как учитывается геометрия белка

Справочник к флагам `--protein_edge_mlp` / `--protein_edge_attention`
(`architecture/protein_encoder.py`, `architecture/edge_geometric_conv.py`,
`architecture/protein_edge_geometry.py`).

## Общая часть: откуда берётся геометрия

Оба флага включают один и тот же геометрический edge-encoding вместо простого
3-мерного Voronota-контакта `(distance, area, boundary)`. Триггер —
`use_structured_edges = use_edge_attention or use_edge_mlp` в
`protein_encoder.py:52`, который заставляет граф-строитель вызывать
`structured_edge_features()` из `protein_edge_geometry.py`.

Эта функция (реализация Ingraham et al. 2019, §3.3.1) строит **25-мерный
SE(3)-инвариантный вектор** на каждое направленное ребро из жёстких фреймов
остатков (ротация + Cα-трансляция):

- 16 RBF-бинов расстояния между Cα (`protein_edge_geometry.py:100`)
- локальный вектор направления к соседу, повёрнутый в систему координат
  остатка-референса (`:93`)
- кватернион относительной ориентации фреймов (`:97`)
- `log(area)` и `log(boundary/area)` — геометрия исходного Voronota-контакта

Это именно то, чем `--protein_edge_mlp`/`--protein_edge_attention` отличаются
от обычного GATv2/GINE-графа: там ребро несёт только
`(distance, area, boundary)`, тут — полную относительную позу соседа.

## Разница между MLP и attention в том, как это потребляется

Оба варианта реализованы в `edge_geometric_conv.py` как conv-слои с одинаковой
сигнатурой `(x, edge_index, edge_attr) -> x`.

**`EdgeMLPConv`** (Dauparas/ProteinMPNN, §3.4.2):

```
m_ij = MLP([h_i, e_ij, h_j])   # 3 линейных слоя + GELU
h_i' = Σ_j m_ij / lambda        # lambda=30 по умолчанию, --protein_edge_mlp_lambda
```

Геометрия ребра `e_ij` конкатенируется вместе с признаками обоих узлов и
прогоняется через нелинейный MLP — сеть сама учится, как признаки соседа и
геометрия взаимодействуют. Никакой избирательности при агрегации нет: все
соседи просто суммируются, а сумма делится на константу (не на степень узла и
не на attention-веса).

**`EdgeAttentionConv`** (буквально Ingraham §3.3.2):

```
q_i = W_Q h_i
k_ij, v_ij = W_K/W_V([e_ij, h_j])
w_ij = softmax_j(q_i^T k_ij / sqrt(d))
h_i' = Σ_j w_ij v_ij
```

Здесь query строится только из `h_i` (без геометрии), а geometry входит в
key/value вместе с признаками соседа. Веса `w_ij` нормализуются softmax'ом по
всем соседям узла — соседи буквально конкурируют за «внимание», и сеть может
подавить геометрически нерелевантные контакты, занулив их вес.

## Итог

- Геометрию оба варианта видят одинаково — тот же 25-мерный
  фрейм-инвариантный вектор.
- Разница — в механизме агрегации: `edge_mlp` пропускает `(h_i, e_ij, h_j)`
  через общий нелинейный MLP и суммирует с фиксированной нормировкой (без
  конкуренции между соседями за вес); `edge_attention` использует geometry
  только в key/value и агрегирует через softmax-взвешенную сумму, где веса
  адаптивны и нормированы (сумма = 1), что даёт explicit relevance-gating,
  которого у MLP-варианта нет.
