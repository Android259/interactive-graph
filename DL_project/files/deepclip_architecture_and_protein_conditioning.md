## 0. Что уже есть — точка отсчёта

`architecture/deepclip.py` строит `DeepCLIP` **отдельно** от белковой башни: нет
`Protein_encoder`, нет `cross_attention.py`, нет `Final_Layer` (docstring файла,
строки 26-31). На вход попадает только one-hot SMILES; белок присутствует только
через то, какая подвыборка данных вообще видна модели (`--family_only`).

Единственный уже реализованный мост — `--deepclip_protein_gate` (строки 151-191,
250-317): пул скалярных карманных дескрипторов (`PROTEIN_DESCRIPTOR_NAMES` /
`POCKET_CHEMISTRY_DESCRIPTOR_NAMES`, `dataloader/pair_descriptors.py:141-260`) →
маленький MLP → `tanh` → **один** вектор из `hidden` мультипликативных весов,
центрированных по среднему на 1.0 (строки 290-292), плюс один аддитивный bias
(строка 293), приложенных ПОСЛЕ readout (строка 317). Вес идентичен для КАЖДОЙ
позиции молекулы — `weights.unsqueeze(1)` (строка 292) транслируется по всей оси
позиций без изменений.

Измеренный failure mode (`files/deepclip_gate_and_subclass_plan.md` §4, коммент в
коде строки 162-289): на data-starved семьях (GLTP/GLTPD1, ~25-30 позитивов)
немультицентрированный мультипликативный гейт схлопывал specificity ровно в 0.0
или 1.0 у большинства seed'ов, потому что единый вектор, применённый одинаково ко
всем позициям, при совпадении знака по всем каналам вырождает сумму профиля в
константу вне зависимости от последовательности. Bias-only почти не помог (7/10 →
6/10 коллапсов). Причина, названная в коде явно (строки 278-289): "a protein whose
gate departs uniformly scales the whole profile toward one sign, regardless of
sequence" — это **главный критерий**, по которому в разделе 2 оценивается каждое
предложение: даёт ли механизм протеину способ сдвинуть ВЕСЬ профиль в одну сторону
одним числом, или нет.

## 1. Литература (коротко, зачем каждая цитата приведена)

- **DeepDTA** (Öztürk et al., *Bioinformatics* 2018, arXiv:1801.10193) — два
  параллельных 1D-CNN (белковая последовательность, SMILES), результаты
  конкатенируются и идут в FC. Каноничный пример позднего слияния "две башни →
  concat → голова", без взаимного влияния башен друг на друга до самого конца.
- **GraphDTA** (Nguyen et al., *Bioinformatics* 2021) — тот же паттерн позднего
  слияния, только лиганд — граф (GNN), а не CNN по SMILES; белок остаётся CNN по
  последовательности. Подтверждает, что "две отдельные башни + concat" переносимо
  между разными энкодерами лиганда.
- **MONN** (Li et al., *Cell Systems* 2020, biorxiv 2019.12.30.891515) — явный
  pairwise-модуль атом↔остаток, обучаемый на ОТДЕЛЬНОЙ супервизии
  (экспериментально известные нековалентные контакты из PDBbind-подобных данных),
  не просто attention поверх бинарной метки связывания. Их собственный вывод,
  явно заявленный в статье: attention-модели, обученные ТОЛЬКО на метке
  affinity/interaction, не восстанавливают физически осмысленные atom-residue
  контакты без прямой супервизии контактов.
- **CAPLA** (*Bioinformatics* 39(2), 2023, btad049) — cross-attention между
  представлением кармана (включая физико-химические свойства остатка) и SMILES
  лиганда на уровне последовательностей, без 3D-структуры на входе.
- **PLAPT** — ProtBERT + ChemBERTa эмбеддинги, "branching neural network"
  (по сути тот же DeepDTA-паттерн конкатенации, но с предобученными
  трансформерами вместо CNN с нуля).
- **FiLM** (Perez et al., AAAI 2018, github.com/ethanjperez/film) — условная
  affine-модуляция признаковой карты: `γ, β = f(condition)`, `x' = γ·x + β`,
  применяется по каналам, одинаково для всех пространственных/временных позиций.
- **HyperNetworks** (Ha, Dai, Le, arXiv:1609.09106, 2016) — сеть, порождающая
  ВЕСА другой сети по условию (a genotype net generating a phenotype net's
  weights); их же собственный эксперимент — генерация нешаренных весов LSTM.

## 2. Предложения

Каждое — независимый флаг в духе `--deepclip_protein_gate`: выключен по
умолчанию, при выключении не меняет поведение, при включении инициализируется
так, чтобы старт совпадал с уже опубликованным DeepCLIP или с текущим кодом.

### 2.1 FiLM-модуляция карты свёртки, до LSTM — `--deepclip_protein_film`

**Механизм.** `γ, β = MLP(pocket_descriptors)`, размер `2 × filters × len(widths)`
(при дефолтах `filters=1`, `widths=5` — это `2×5=10` чисел). Встраивается сразу
после `self.conv_act(scanned)` (deepclip.py:219), до цикла `extra_convs` или
после него — до LSTM: `scanned = scanned * γ.unsqueeze(-1) + β.unsqueeze(-1)`.

**Отличие от `--deepclip_protein_gate`.** Гейт действует ПОСЛЕ LSTM, на уже
просуммированных по направлениям скрытых состояниях (10 каналов, физический
смысл — "профиль"); FiLM действует ДО LSTM, на выходе свёрток (5 каналов,
физический смысл — "локальный отклик мотив-детектора в этой позиции"). Разница
не косметическая: LSTM интегрирует уже протеин-обусловленный сигнал по всей
последовательности, а не переприоритизирует готовый профиль постфактум.

**Деградация к дефолту.** Обнуление последнего слоя MLP → `γ=1, β=0` — тождество,
идентично published DeepCLIP при старте (тот же приём, что уже используется для
гейта, deepclip.py:186-190).

**Риск коллапса specificity.** Тот же механизм в чистом виде: `γ, β` — ОДИН
вектор на пару, транслируемый по ВСЕЙ оси позиций одинаково — ровно то, что код
сейчас называет причиной коллапса (deepclip.py:278-282). Без переноса того же
бounding/центрирования (`tanh`, mean-centering по каналам — строки 260-291) сюда
эта версия воспроизводит задокументированный коллапс, просто на слой раньше.
Никаких новых данных, подтверждающих, что более раннее место внедрения снимает
проблему, нет — она заявлена как гипотеза, а не измеренный результат.

### 2.2 Гиперсети, генерирующие добавку к фильтрам свёртки — `--deepclip_protein_hyperconv`

**Механизм.** Вместо переприоритизации готового профиля — генерация
per-protein АДДИТИВНОЙ добавки `Δ` к самим весам свёртки: `Δ = MLP(pocket)`,
reshape в `(filters, conv_in, width)` на каждую из `widths`, `effective_weight =
base_weight + Δ`. При нулевой инициализации последнего слоя MLP — `Δ=0`, старт
идентичен текущим общим фильтрам. Требует ручного `F.conv1d` с per-sample весом
(через group-conv по батчу) вместо `nn.Conv1d`-модуля — это не деталь, а
реальная переработка forward.

**Отличие от гейта/FiLM.** Гейт и FiLM переприоритизируют выход уже
ЗАФИКСИРОВАННОГО, протеин-слепого детектора мотивов; гиперсеть меняет, КАКОЙ
мотив детектируется, для каждого белка отдельно (буквально идея Ha et al. 2016 —
conditioning на веса, а не на активации).

**Стоимость.** При дефолтах (`vocabulary=20`, `widths=(4,5,6,7,8)`, `filters=1`)
суммарный размер весов свёртки — `20·(4+5+6+7+8)=600` чисел. MLP, порождающий эти
600 чисел из `gate_hidden=8`-мерного скрытого слоя, добавляет ~`8×600+600≈5400`
параметров — БОЛЬШЕ, чем весь DeepCLIP целиком (~1960 параметров при этих же
widths, `files/deepclip_gate_and_subclass_plan.md` §7, таблица). На семье
GLTP/GLTPD1 (~25-30 позитивов) это радикально хуже соотношение параметров к
данным, чем у текущего гейта (`hidden+1=9` выходов, ~186 параметров).

**Риск коллапса.** Другая поверхность отказа, не то же самое, но родственная:
если `Δ` для одного белка равномерно положителен по всей таблице `(width ×
vocab)`, получившийся фильтр реагирует "на что угодно" — фильтр становится
детектором длины, а не мотива, то есть тот же итоговый провал ("профиль отражает
длину, а не последовательность"), про который уже предупреждает docstring
readout'а (deepclip.py:303-308), только достигнутый через другой путь.
Контрмера в духе уже применённой (mean-centering по каналам, строки 290-291) —
центрировать `Δ` по оси алфавита на каждый `(width, filter)`, чтобы белок не мог
равномерно поднять отклик на ЛЮБОЙ символ, только перераспределить между
символами. Не измерено.

### 2.3 Позиционно-локальный, content-dependent гейт — расширение `--deepclip_protein_gate`

**Механизм.** Сейчас `gate_input` — только карманные дескрипторы, один вектор на
пару, и веса транслируются на все позиции одинаково (`weights.unsqueeze(1)`,
строка 292). Предложение: конкатенировать в `gate_input` ещё и `states[b, pos,
:]` самой LSTM-позиции — `gate_out[b, pos] = MLP(concat[pocket, states[b, pos,
:]])`. Вес каждой позиции теперь зависит и от белка, и от того, ЧТО локально
находится в этой позиции молекулы, а не только от того, какой это белок.

**Отличие от текущего гейта.** Прямое: убирается именно то свойство, которое код
сейчас называет причиной коллапса — идентичность веса по всем позициям одной
молекулы для данного белка (deepclip.py:292, `.unsqueeze(1)`).

**Насколько это реально решает коллапс, а не просто прячет.** Частично и не
гарантированно: если MLP научится игнорировать `states[pos]` и читать только
карманную часть входа, ничего не мешает ему выродиться обратно в старый
константный по позициям гейт — архитектура делает коллапс НЕобязательным, но не
делает его невозможным. Нужен аналог уже применённого трюка (mean-centering по
каналам, строки 290-291), только по ОСИ ПОЗИЦИЙ: центрировать `gate_out` по
среднему за все позиции ОДНОЙ молекулы, чтобы "постоянная по позициям
составляющая" гейта была архитектурно занулена и оставалась только
перераспределение веса между позициями — позиционный аналог уже работающей
идеи, не измеренный.

**Стоимость.** MLP работает на каждой позиции, а не на паре → FLOPs растут с
длиной последовательности × батчем, а не только с батчем; количество параметров
самой MLP сопоставимо с текущим гейтом (вход шире на `hidden=10`).

**Связь с литературой.** Структурно это огрублённая версия того, что делает
cross-attention CAPLA (Bioinformatics 2023, см. §1) или pairwise-модуль MONN на
уровне пары (позиция лиганда, карман) — только без настоящего множества "ключей"
со стороны белка (карман здесь всё ещё один пулинг-вектор, не набор остатков),
так что это промежуточная точка между текущим гейтом и следующим предложением
(2.4).

### 2.4 Cross-attention с реальными остатками кармана, без пулинга — `--deepclip_pocket_cross_attention` (крупное изменение)

**Механизм.** Вместо пулинг-вектора из ~13-20 карманных скаляров — набор реальных
per-residue представлений кармана (выход `Protein_encoder`'а, GATv2, или
спроецированный ESM3 `[N, 1536]`). Один cross-attention слой (по образцу уже
работающего `architecture/cross_attention.py`, контракт в
`architecture/AGENTS.md:42-43`: `[N_lipid, N_protein]`-маска, `True` = запрещено)
между LSTM-состояниями DeepCLIP (query, по позиции) и остатками кармана
(key/value), результат — аддитивный контекст на каждую позицию, прибавляемый к
`states` перед суммированием профиля.

**Отличие от 2.1-2.3.** Качественно другой порядок информации: 2.1-2.3 читают
ПУЛИНГ-вектор из ~13-20 скаляров на карман (`PROTEIN_DESCRIPTOR_NAMES` /
`POCKET_CHEMISTRY_DESCRIPTOR_NAMES`); это предложение впускает НАСТОЯЩУЮ
структуру остатков — то есть буквально ломает инвариант docstring'а deepclip.py
(строки 26-31): "InteractionClassification builds this module ALONE... no
protein encoder". Это не расширение флага, а отдельная, гораздо более крупная
переделка — явно помечаю это, а не маскирую под ту же категорию, что 2.1-2.3.

**Риск коллапса.** Структурно мягче: softmax-веса внимания по набору ключей
суммируются в 1 НА КАЖДУЮ ПОЗИЦИЮ, у механизма нет свободного мультипликативного/
аддитивного параметра вне нормализованных весов внимания — единым знаком сдвинуть
весь профиль сложнее, чем у гейта. Но это утверждение о СТРУКТУРЕ, не измерение
на этом проекте.

**Явная оговорка от литературы.** MONN (Li et al. 2020, §1) — их собственный
результат: attention, обученный ТОЛЬКО на бинарной метке связывания (без прямой
супервизии atom-residue контактов), не восстанавливает физически осмысленные
контакты. В этом датасете нет разметки контактов остаток↔SMILES-символ (в
интеракционной таблице есть только бинарная метка пары), поэтому если это
предложение подаётся как "читаемая карта, какой остаток кармана отвечает за
какой фрагмент SMILES" — это претензия, которую MONN прямо предостерегает не
делать без отдельной супервизии; предсказание класса это может улучшить, но
интерпретируемость профиля как физического контакта — нет, пока нет такой метки.

**Философское несоответствие.** DeepCLIP как метод (Grønning et al. 2020,
цитируется в docstring, строки 1-24) — это специально МАЛЕНЬКАЯ модель на
собственных данных одного белка (~1.9-2.1k параметров). Протащить сюда GATv2/
ESM3-башню — размер параметров вырастет на порядки, что противоречит самой
причине, по которой DeepCLIP вообще выбран для `--family_only` режима. Это
компромисс, который стоит явно проговорить, а не молчаливо принять вместе с
кодом.

### 2.5 "Бедная протеиновая DeepCLIP": зеркальная conv+BiLSTM башня по остаткам кармана в порядке цепи, позднее слияние — `--deepclip_protein_tower`

Один из двух буквальных прочтений "graph pass through deepclip": здесь берётся не
граф, а порядок цепи (последовательность остатков кармана), и через него
прогоняется АРХИТЕКТУРА DeepCLIP, применённая к белку вместо липида.

**Механизм.** Вторая, независимая conv+BiLSTM ветка, архитектурно идентичная
lipid-ветке DeepCLIP (несколько Conv1d разной ширины → ReLU → BiLSTM → сумма
профиля), но читающая остатки кармана В ПОРЯДКЕ ЦЕПИ (порядок узлов уже доступен
в `protein_graph_builder.py`) вместо one-hot SMILES — алфавит либо 20
аминокислот one-hot (прямая аналогия DeepCLIP-алфавита), либо per-residue вектор
скалярных признаков (буриедность, гидропатия и т.д. — "разложенный по позициям"
аналог `PROTEIN_DESCRIPTOR_NAMES`, которые сейчас пулятся в один вектор на
карман). Результат — второй скор/профиль со стороны белка на пару, сливаемый с
lipid-скором DeepCLIP КОНКАТЕНАЦИЕЙ + маленькой FC-головой (буквально паттерн
DeepDTA/PLAPT, §1), а не гейтингом одной ветки другой.

**Отличие от гейта.** Всё до момента слияния строго протеин-слепо для липидной
ветки и липид-слепо для протеиновой — никакого протекания сигнала между ними до
самого конца. Это семейство "две башни, позднее слияние" в противовес семейству
"одна башня, условленная другой" (2.1-2.4).

**Риск коллапса — явно НЕ решён, а перенесён и, возможно, ухудшен.**
Конкатенация + FC — строго БОЛЕЕ выразительный комбинатор, чем явное разделение
"мультипликативный вес / аддитивный bias" текущего гейта, и большая
выразительность не эквивалентна большей устойчивости на 25-30-позитивной семье —
скорее наоборот, у FC больше степеней свободы запомнить "этот белок → такой-то
ответ", и ни один из уже применённых защитных приёмов (`tanh`-ограничение,
центрирование по каналам) не переносится на generic FC автоматически. Чтобы
унаследовать гарантию "старт = published DeepCLIP", FC пришлось бы
инициализировать так, чтобы читать ТОЛЬКО lipid-скор (зануление веса при
protein-скоре на старте) — тот же дисциплинированный zero-init, что уже
применяется к гейту (deepclip.py:189-190), просто на другом слое.

**Стоимость.** Вторая башня — это ещё ~1.9-2.8k параметров поверх текущих
~1960-2140 (`files/deepclip_gate_and_subclass_plan.md` §6, таблица параметров) —
рост размера сети почти вдвое, против ~186 параметров у существующего гейта. Раздел
4 ниже даёт прямую причину относиться к этому скептически: базовая модель уже
схлопывается на 10 позитивах БЕЗ единого лишнего параметра — удвоение параметров на
той же выборке эту проблему не решает по построению.

### 2.6 Токенизация: белковые псевдо-токены в ТОЙ ЖЕ последовательности — `--deepclip_protein_tokens`

Второе буквальное прочтение "токенизация" — не отдельная ветка, а расширение
самого входного алфавита.

**Механизм.** `SMILES_VOCABULARY` (`dataloader/smiles_tokens.py:52-58`, 20
символов) расширяется небольшим числом "белковых" токенов (например, по одному
на семью, или по дискретизированным бинам карманной химии), которые
приписываются В НАЧАЛО (или в конец) one-hot последовательности перед
свёрточным сканом — тот же тензор `dense` (deepclip.py:203), просто с
несколькими дополнительными "символами" впереди.

**Отличие от остальных предложений.** Это единственный вариант, где условие на
белок входит НЕ как модуляция весов/профиля, а как часть самой
последовательности символов, наравне с химией — механизм доставки принципиально
другой: свёрточное окно шириной 4-8 напрямую видит белковый токен только для
позиций, отстоящих от него не дальше `width-1` символов; на позиции в глубине
молекулы (26-165 символов) сигнал может дойти только через рекуррентную память
BiLSTM, а не напрямую через свёртку.

**Деградация к дефолту.** НЕ бесплатна и НЕ такая же чистая, как у остальных
предложений: расширение `SMILES_VOCABULARY` меняет ширину входа свёрток, то есть
меняет `number_of_parameters` и **инвалидирует существующие чекпойнты** —
явное предупреждение уже стоит в самом файле (`dataloader/smiles_tokens.py:31-36,
47-51`, "widening the tuple invalidates checkpoints"). Ни один из остальных пяти
пунктов этого недостатка не имеет.

**Риск коллапса.** Иной по механике, не измеренный: белковый токен на старте
последовательности даёт BiLSTM одно и то же начальное скрытое состояние для
каждой молекулы этого белка — то есть потенциально тот же "константный сдвиг для
всех молекул белка", только через затухающую рекуррентную память, а не через
явный фиксированный скаляр. Насколько сильно затухает влияние начального токена
за 26-165 символов — не измерено для ЭТОЙ задачи. Косвенно, но не напрямую
подтверждающее наблюдение есть: `analysis/deepclip_headgroup_probe.py`
(`files/deepclip_gate_and_subclass_plan.md` §7) уже показал, что текущий
conv+BiLSTM (широты 4-8) достаёт до цифры замыкания кольца через 32-38 символов
БЕЗ более широкого фильтра — то есть LSTM в этом коде практически удерживает
контекст на десятки символов. Но это измерение про ДРУГУЮ задачу (различение
голов HexCer/SM), не про удержание белкового токена конкретно, поэтому это
слабое косвенное, а не прямое подтверждение.

## 3. Что объединяет все шесть (и что не решено ни одним)

- Все шесть — опциональные флаги, ни один не меняет поведение при выключении;
  каждому нужна своя версия zero-init/identity-старта, аналогичная уже принятой
  для `--deepclip_protein_gate` (deepclip.py:186-190) — ни один не наследует её
  автоматически, каждый нужно спроектировать заново под свою форму параметров.
- Ровно один критерий коллапса проходит через всё: может ли протеиновый сигнал
  сдвинуть ВЕСЬ профиль одним знаком одним числом. 2.1 и 2.2 без явного
  ограничения (bounding/mean-centering по своей оси) наследуют этот риск
  напрямую; 2.3 убирает его частично (по построению, не гарантированно); 2.4
  структурно мягче (softmax-нормировка), но не измерено на этом проекте; 2.5
  переносит риск в FC-комбинатор без встроенной защиты; 2.6 заменяет риск другим
  (затухание рекуррентной памяти, тоже не измеренное).
- Существующий `--deepclip_gate_weight_decay` (`training/
  read_configuration.py:346-353, 3537`) — отдельная группа оптимизатора для MLP
  гейта — механически применим к любому из 2.1-2.3, 2.5 без изменений в самом
  флаге, если их параметры зарегистрировать в той же именованной группе.
- Ни одно предложение не прогонялось. Любые числа "риска коллапса" выше — это
  перенос уже измеренного механизма (§0), не новое измерение.
- Раздел 4 добавляет фон, который ни одно из шести предложений само по себе не
  меняет: базовая, protein-blind DeepCLIP уже схлопывается в константу на
  достаточно маленькой выборке БЕЗ какого-либо протеинового входа вообще. Любое
  предложение из раздела 2 решает задачу "дать протеину способ повлиять на
  профиль, не ломая при этом то, что уже работает" — но не задачу "сделать
  10 позитивов достаточными", которая является проблемой данных, а не
  архитектуры.

## 4. Эмпирика: что происходит при попытке обучить DeepCLIP на одном белке

### 4.1 Такой прогон уже существует — не гипотеза, а 25 завершённых запусков

`ProteinDomain` "ML" содержит РОВНО один белок — GM2A
(`training/read_configuration.py:87-137`, `EXCLUDED_SUBGROUPS_BY_NAME["ML"] =
["GM2A"]`). Это единственная однобелковая "семья" среди девяти канонических групп
(`scripts/settings.sh:131-139`) — у остальных восьми от 2 (GLTP, OSBP,
LBP_BPI_CETP) до 10 белков (lipocalin). Раз `--family_only=<группа>` ограничивает
таблицу до `ProteinDomain` этой группы (`dataloader/Dataloader.py:149-166`), то
`--family_only=ML` МЕХАНИЧЕСКИ равнозначно "обучить DeepCLIP на одном белке" — не
нужно ничего специально урезать.

Это уже прогнано: `ML` — одна из девяти групп, по которым уже прошли все пять
базовых deepclip-свипов (`deepclip_f1_const_mean_ep120`, `deepclip_f1_normal_
mean_ep120`, `deepclip_f4_normal_mean_ep120`, `deepclip_f8_normal_mean_ep120`,
`deepclip_f1_const_sum_ep120` — bare `--family_only`, `launch/submit_grid.sh`
подставляет группу, `scripts/arg_files/deepclip_f1_const_mean_ep120.md:17-20`).
В `metrics_summary.csv` это ровно 25 строк (`family_only=="ML"`: 5 конфигураций ×
5 seed'ов, за вычетом ещё не долитых).

### 4.2 Результат: тотальный, безусловный коллапс к константе

Все 25 строк, без единого исключения:

- `label_positive_fraction == 0.5` (все 25)
- `balanced_accuracy == 0.5` (все 25, ровно, не "около")
- `(sensitivity, specificity)` — ровно `(1.0, 0.0)` или ровно `(0.0, 1.0)`, никогда
  ничего среднего

Примеры прямо из таблицы (столбцы `label / seed / sensitivity / specificity /
balanced_accuracy / number_of_parameters`):

```
deepclip_f1_const_mean_ep120    1  1.0 0.0 0.5  1960
deepclip_f1_const_mean_ep120    2  0.0 1.0 0.5  1960
deepclip_f1_normal_mean_ep120   0  1.0 0.0 0.5  1960
deepclip_f4_normal_mean_ep120   4  0.0 1.0 0.5  4960
deepclip_f8_normal_mean_ep120   1  0.0 1.0 0.5  8960
deepclip_f1_const_sum_ep120     0  1.0 0.0 0.5  1960
```

Паттерн не зависит НИ ОТ ОДНОГО варьируемого измерения: числа фильтров (1/4/8 →
1960/4960/8960 параметров), инициализации свёртки (constant/normal), readout
(mean/sum), seed'а (0-4). 25 из 25 запусков дают классификатор, который на тесте
предсказывает ОДИН класс для ВСЕХ объектов — какой именно класс, определяется
seed'ом, а не архитектурой.

### 4.3 Почему: прямые данные плюс правдоподобный (не измеренный построчно) механизм

Прямо измерено из `data/Processed_Negative_Interaction_Corrected_Domains_SMILES_
Fixed_CandidatesCompleted_Deduplicated.csv` (таблица `9905` строк / `634`
позитива, "table rebuilt 2026-08-24"): у GM2A **283 кандидата-липида, 10
позитивов (3.5%)**. Это пятое по малости число позитивов среди 34 белков таблицы —
меньше только у пяти белков с 1 позитивом (RBP1/RBP4/RBP5/CRABP2/BNIPL) и трёх с
2-3 (SEC14L5/ATCAY/OSBPL5/OSBPL9/SEC14L4). У КАЖДОГО белка ровно 283 строки в
таблице (один и тот же кандидатный список липидов проверен против каждого белка) —
так что 283/10 — это весь бюджет данных GM2A, а не следствие какого-то фильтра.

Ни один из пяти deepclip-свипов не ставит `--balanced_proteins` или
`--balance_negatives_by_family` — значит применяется дефолтный сэмплер
негативов, `split_and_sample_interactions` (`dataloader/sampler.py:10-17`):
все позитивы остаются, негативы берутся случайной выборкой `frac=0.056` (5.6%).
Разбиение на train/valid/test при `--family_only` без `--excluded_groups`/
`--test_group` идёт обычным путём: 85% строк в train (`dataloader/Dataloader.py:
1599`), из оставшихся 15% — 50/50 в valid/test (`dataloader/Dataloader.py:1664-
1665`).

**Вывод из кода, не измерение по фактическому числу строк в каждом сплите**: на
283-строчном однобелковом срезе это НЕИЗБЕЖНО оставляет и валидационный, и
тестовый кусок GM2A в буквальном смысле из единиц строк. При таком размере любой
классификатор, выдающий константу на весь тест (все 0 либо все 1), АВТОМАТИЧЕСКИ
даёт `sensitivity`/`specificity` ровно `{0, 1}` и `balanced_accuracy` ровно `0.5`
— что численно неотличимо от наблюдаемого. Я не инструментировал загрузчик, чтобы
подтвердить точные размеры сплитов построчно — это правдоподобный, согласующийся
с кодом механизм, а не отдельно проверенный факт, и он не исключает, что модель и
правда выучивает вырожденную константу, а не просто "не может ошибиться иначе"
из-за размера тестового среза — оба объяснения дают один и тот же численный
паттерн, различить их эта таблица не позволяет.

### 4.4 Сравнение с более крупными семьями: похоже, дело в числе позитивов, а не белков

- **GLTP** (2 белка, 33+29=62 позитива), "тёплый" контроль без гейта,
  `deepclip_gltp_warm_ep120`, seed 0 (единственный завершённый на данный момент —
  `files/deepclip_gate_and_subclass_plan.md` §8 фиксировал этот прогон
  незавершённым на момент записи, так что обобщать на другие seed'ы нельзя):
  `balanced_accuracy=0.95`, `sensitivity=1.0`, `specificity=0.9` — настоящий,
  НЕ вырожденный результат.
- **CRAL-TRIO** (9 белков) в тех же пяти vanilla-свипах (та же пятёрка
  конфигураций, применённая к группе CRAL-TRIO, ~0.3-0.59 доли позитивов в
  зависимости от прогона): `balanced_accuracy` градуирован по всему диапазону
  0.41-0.85 в зависимости от seed'а и конфигурации — НЕ прижат к экстремальным
  `{0, 1}` в sensitivity/specificity. Настоящий сигнал, не коллапс.
- **Тот же CRAL-TRIO**, но урезанный `--lipid_subclass` до PA-специфичной подвыборки
  (`deepclip_cral_trio_protein_gate_subclass_pa_ep120` и варианты, доля позитивов
  0.47, но абсолютное число резко меньше из-за подкласса): паттерн `(1.0,0.0)` /
  `(0.0,1.0)` снова появляется в БОЛЬШИНСТВЕ (не всех) seed'ов — то же самое
  вырождение, что у ML, хотя формально это девятибелковая семья.

Согласованный вывод по всем четырём точкам: порог коллапса определяется не числом
белков в `--family_only`-группе, а числом позитивов, реально доступных модели и
eval-срезу после сэмплинга и (если есть) `--lipid_subclass`-фильтра. GLTP и
CRAL-TRIO (vanilla, десятки позитивов) коллапса избегают; ML (10 позитивов) и
CRAL-TRIO/PA-подкласс (меньше позитивов после урезания, несмотря на 9 белков в
номинальной семье) — нет.

### 4.5 Что это значит для раздела 2 и для "попробовать другой один белок"

Критерий коллапса из §0 (может ли протеиновый сигнал сдвинуть ВЕСЬ профиль одним
числом) объясняет механизм именно ДЛЯ ГЕЙТА. Раздел 4 показывает более базовый и
более раннй факт: САМА базовая архитектура, БЕЗ единого протеинового входа,
уже схлопывается в константный классификатор, как только обучающая/eval-выборка
становится настолько маленькой (10 позитивов). Это имеет прямое следствие для
оценки 2.1-2.6: ни одно из них не адресует ЭТУ проблему в первом порядке — они
строят мост между белками ВНУТРИ семьи (2.1-2.4), либо добавляют вторую башню
(2.5), либо меняют алфавит (2.6), но ни одно не увеличивает число позитивов у
ОДНОГО белка. В частности 2.5 (вторая, протеиновая башня) на этом фоне выглядит
хуже, а не лучше: раздел 2.5 уже отмечал, что она примерно УДВАИВАЕТ число
параметров без встроенной защиты от переобучения — на 10-позитивной выборке это
усугубляет, а не решает то, что уже видно в разделе 4.2 при БАЗОВЫХ ~1960-8960
параметрах.

Отдельно: если захочется проверить это на ДРУГОМ одиночном белке (не GM2A) —
`--family_only=<группа>` даёт единственный белок только для группы `ML`. Для
любого другого белка внутри многобелковой семьи (например, изолировать GLTP от
GLTPD1) нужна комбинация `--family_only=<семья> --drop_proteins=<остальные члены
семьи>` (`--drop_proteins`, `dataloader/Dataloader.py:172-186`, до сих пор
использовался только для гигиенических удалений вроде PITPNA, не для этой цели)
— такого прогона в `scripts/arg_files/` сейчас нет, это НЕ измерено.
